本科毕设
选题与技术选型的几个判断

这是我做毕设前记下的东西：怎么判断题目值不值得做、技术栈怎么选、什么算「有工作量」。还没到答辩，所以只写已经想清楚的部分。

毕设选题技术选型笔记

一、什么算「有工作量」

毕设最容易翻车的地方不是做不出来，而是做出来了但被判定「工作量不够」。所以选题时就要想清楚：什么算工作量。

我记下的判断标准是三个维度：

  • 多角色：系统里有几种不同的使用者，各自有不同权限和流程
  • 多模块：能拆成几个独立功能块，而不是一个页面调一次 API
  • 大模型 API 的实际调用：不是套壳，而是有真实的调用链路和工程处理

反过来，要避免的是「外挂大模型的水项目」——一个输入框 + 一次 API 调用 + 一个输出框，这种答辩时很难说明技术含量。

二、选题方向的判断

我当时的结论是：从知网找已有的研究方向，而不是凭空想题目。原因很实际——

  • 知网上的论文能告诉你这个方向有没有人做过、做到什么程度
  • 有前人论文意味着有可参考的技术路线和评价方法，不至于从零摸索
  • 如果搜不到相关论文，可能说明这个方向不被学术认可，或者太难做不出来

另一个思路是在已有工作上补一个工程痛点，而不是重新发明一个系统。比如在 RAG 或 Agent 的基础上，解决：

  • 记忆管理——上下文超长时怎么压缩、怎么决定记住什么、忘掉什么
  • 工具权限约束——Agent 能调用哪些工具、边界在哪
  • Spec 校验——怎么防止任务执行过程中偏离原始意图（任务漂移）

这类「补一个点」的题目，比「做一个全新的 XX 系统」更容易讲清创新点，也更可控。

三、技术栈怎么选

我当时记下了三个 Python Web 框架的取舍：

  • Django：适合多角色系统。自带 admin、权限、ORM，用户角色和后台管理几乎是现成的
  • FastAPI：适合快速完成接口。异步性能好，写 API 快，适合前后端分离
  • Flask：轻量级，适合小工具或需要完全自定义的场景

判断依据是「你的系统是重后台管理，还是重接口」：

需要多角色权限 + 后台管理  →  Django
主要是 API + 前端另做      →  FastAPI
只是个小工具 / 要高度自定义 →  Flask

四、关于 AIGC 检测

我当时记了一句：「人的表达，独特，不让 AI 预测」。

理解这句话的关键是——AI 生成的内容有统计上的可预测性。它倾向于用常见的句式、常见的论证结构、常见的中文表达。所以如果想让论文不被判为 AI 生成，核心不是「改几个词」，而是：

  • 加入具体的、不可预测的细节——你实际遇到了什么问题、用了什么工具、数据长什么样
  • 用你自己的表达方式——哪怕不够漂亮，但是你的句子
  • 论证逻辑要是你自己的——为什么这么设计，不是因为「常见」，而是因为你的具体约束

这一点其实和写博客是同一件事：只有你自己经历过的细节，是 AI 猜不出来的。

五、论文排版工具

论文公式和排版用 LaTeX，这是代码式的排版系统——写标记语言，编译成 PDF。

本科论文一般是学校提供 Word 模板，但公式多的章节（尤其是理工科）用 LaTeX 排版后再转 PDF 会整齐很多。如果学校允许 PDF 提交，值得花半天学基础语法。
