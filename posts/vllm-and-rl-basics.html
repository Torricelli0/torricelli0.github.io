vLLM 册子、Infra 分层
与 RL 微调名词梳理

把最近查的两组概念整理成一篇：一组是 vLLM 与推理 Infra 的关系，另一组是 LoRA / SFT / RL / PPO / GRPO 到底谁属于谁。

vLLMINFRARLLORA

一、vLLM 册子是什么

行业里说的「vLLM 册子」分两种，日常开发多指速查手册，少数场景指官方完整 PDF 文档。

1. vLLM Cheatsheet（最常说的册子）

把 vLLM 的启动参数、并行配置、量化、LoRA、监控、分布式部署命令、报错解决方案浓缩成一份，线上调参、部署时直接复制，不用翻长文档。典型内容包括：

  • 安装、单卡启动、OpenAI 兼容服务命令
  • 张量并行 / 流水线并行多卡参数
  • GPTQ / AWQ / FP8 量化配置
  • KV 缓存、显存利用率、并发调度调优参数
  • 分布式集群、Docker、K8s 部署模板
  • 常见报错：显存溢出、NCCL 通信故障排查

2. 官方 PDF 手册

vLLM 官网可下载完整英文文档 PDF，从原理、PagedAttention 源码、架构、分布式全流程讲起，偏学习、面试、深度优化用。

二、vLLM 和 Infra（AI 基础设施）的层级关系

1. 分层架构（从上到下）

  1. 业务应用层：ChatBot、Agent、业务后端
  2. 网关 / 调度 Infra 层（推理 Infra）：K8s、KServe、Ray、模型网关、限流、扩缩容、多模型路由、监控告警、镜像仓库、存储卷
  3. 推理引擎层：vLLM：负责 GPU 底层推理加速、请求批处理、KV 缓存管理
  4. 硬件底座：GPU、服务器、网卡、存储
Infra 是「容器 / 集群平台」，负责把 vLLM 跑起来；vLLM 是「推理内核程序」，真正做大模型生成加速。完整链路：K8s 调度 GPU 节点 → 拉起 vLLM 容器 → 对外提供 LLM API。

三、为什么「Infra 容易，vLLM 内核反而难」

Infra 简单的三个原因

  1. 标准化工具链成熟：Docker 打包 vLLM 镜像、K8s 部署 yaml 与 HPA 自动扩缩容、GPU 调度插件都有通用模板；监控用 Prometheus + Grafana、日志用 ELK，网上脚本复制即用。
  2. 只做资源调度，不碰 AI 底层优化：Infra 工程师关心机器、网络、存储、可用性、负载均衡，不用理解 PagedAttention、连续批处理、KV 缓存碎片、量化精度、CUDA 内核。
  3. 门槛低、资料多：云厂商提供一键部署平台，Terraform、helm 包遍地，有云原生基础的工程师 1–2 周就能搭起生产级推理集群。

vLLM 本身难在哪

  1. 原理门槛高：必须懂 LLM 解码、注意力机制、GPU 显存管理、CUDA 编程、NCCL 分布式通信。
  2. 调参无固定答案：不同模型（7B / 70B / MoE）、不同上下文、不同并发，gpu-memory-utilization、块大小、批处理阈值完全不一样，靠线上压测和深度调试。
  3. 底层坑多：多卡通信故障、量化精度损失、LoRA 热加载冲突、长上下文 KV 缓存溢出、CUDA Graph 兼容问题。
  4. 性能壁垒高：要提升吞吐、降低延迟，需要改内核、适配硬件（昇腾 / AMD）、定制前缀缓存，属于算法 + 系统交叉领域。

一句话共识：Infra = 云原生运维，拼模板与集群稳定性，学习曲线平缓；vLLM 深度调优 / 内核 = AI 系统底层，拼 GPU 与大模型推理原理，门槛高。

两种岗位

  • AI Infra 工程师：搭 K8s 集群、打包 vLLM 镜像、自动扩缩容、监控、发布流水线。
  • 推理优化工程师：读 vLLM 源码、调参数、优化吞吐、修复内核问题、适配多硬件。

四、LoRA / SFT / RL / PPO / GRPO 谁属于谁

这几名词经常混着出现，其实分属两个体系：微调 与 强化学习。

LoRA：参数高效微调

Low-Rank Adaptation。全量微调要更新全部参数，显存开销极大；LoRA 冻结主干权重，只在注意力层插入极小的低秩矩阵，参数量只有原模型的 0.1%–1%。

LoRA 是微调工具，不是强化学习算法，但可以搭配 RL 使用。

SFT：监督微调（常被误写成 str）

Supervised Fine-Tuning。人工整理高质量「指令—回答」样本，有监督地训练模型遵循人类提问。它是 RLHF 的前置基础步骤，本身不属于强化学习。没有 SFT，后续 RL 会不稳定、输出混乱。

RL：强化学习大类

所有靠奖励反馈优化模型的方法都叫 RL。大模型对齐领域特指 RLHF，完整三段流程：

  1. SFT 监督微调（先教会模型指令格式）
  2. RM 奖励模型训练（人类打分数据训练打分模型）
  3. RL 优化（PPO / GRPO 等算法，用奖励更新模型）

PPO：经典 RL 核心算法

Proximal Policy Optimization。RLHF 第三阶段的标准方案，基于奖励模型的分数更新策略模型，同时限制新旧模型差距避免崩溃。

优点是成熟稳定、框架支持完善；缺点是同时要加载策略、价值、参考、奖励四个模型，显存占用极高。

GRPO：PPO 的轻量化替代

Group Relative Policy Optimization，DeepSeek 提出。核心改进是去掉独立价值网络，同一输入生成多条回答组成分组，用组内相对排名计算优势，大幅降低显存。配合 LoRA 可在单卡 7B 模型上完成 RL 对齐。

快速区分

  • LoRA：参数微调技术，不是 RL 算法
  • SFT：监督微调步骤，不是 RL 算法
  • RL：大类统称，PPO / GRPO 都属于它
  • PPO：传统标准对齐算法，资源消耗大
  • GRPO：PPO 轻量化升级，低成本单机可跑

完整链路：基座模型 → LoRA-SFT → 训练 RM → RL（PPO / GRPO）对齐。除此之外还有 DPO、KTO、IPO 等不需要复杂 PPO 循环的对齐算法。
